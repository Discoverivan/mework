# mework contributor instructions

## Source-of-truth boundaries

- Rust domain and core types are authoritative for persisted behavior and public command/event contracts.
- The Rust core is the only component allowed to access SQLite, providers, credentials, Hermes, notifications, and external writes.
- The React renderer uses typed Tauri commands/events and must not hold secrets or call providers directly.
- Route application-wide and background Tauri events through the typed native event bridge in `frontend/app/native-event-bridge.ts` and the typed app event bus in `frontend/app/app-events.ts`. Feature components should subscribe to app events instead of registering duplicate native listeners; keep direct Tauri listeners only for feature-local, window-specific transports such as the Daily Presenter.
- Treat app events as change or invalidation notifications, not as commands that make every subscriber repeat the same external request. Give each refreshable resource one owner that deduplicates refresh work and publishes the resulting state; explicitly revalidate durable caches during startup because the in-memory event bus does not replay events across process restarts.
- Scope pending state and action locks to the affected resource in every section. Independent items should remain usable and support concurrent refreshes and other operations; deduplicate repeated operations on the same item and block conflicting actions on that item. Use a section-wide lock only when operations actually share mutable state or a dependency, and merge concurrent results without overwriting another item's state.
- Jira integrations target Jira Data Center/Server only. Do not use Atlassian Cloud APIs or assume Cloud-specific endpoints, capabilities, authentication, or behavior; use the REST API supported by the configured Data Center/Server instance.
- Every external object is scoped by `(integration_id, object_type, external_id)`.
- Inbox state is a rebuildable read model; user state is persisted separately.
- Workflow runs, Hermes sessions/runs, approvals, and external actions are isolated and durable.

## Safety and product constraints

- Polling is the only external-change ingestion mechanism. Do not add webhook code, endpoints, tables, or acceptance criteria.
- Treat Jira, GitHub, Bitbucket, comments, descriptions, labels, and generated text as untrusted input.
- External writes require explicit human approval and a local idempotency key. Jira task creation is performed by the Rust core through REST, never by Hermes or the renderer.
- Store all provider credentials only through the OS keyring, using isolated services for release (`com.discoverivan.app.mework`) and development (`com.discoverivan.app.mework.dev`). Never commit them, persist them in SQLite, print them, or return them to the renderer. SQLite, logs, diagnostics exports, prompts, frontend bundles, and Git history must not contain tokens or raw authorization headers.
- Until the 1.0.0 release, evolve SQLite with forward compatibility migrations and never rewrite or remove a migration that may already have been applied to a development database. Before releasing 1.0.0, review and consolidate the migration history into a small clean baseline as an explicit release task.
- Do not invent provider fields, signed headers, destination metadata, or fallback values absent from the external contract.
- Product branding is fixed: the production name is exactly `mework` and the development name is exactly `mework-dev`, both lowercase. Do not change their spelling, capitalization, or user-visible/native metadata without an explicit product decision.
- Add localization as part of every new user-facing feature: use translation keys instead of hardcoded renderer copy and provide both English and Russian values in the same change. On first run, initialize the saved language from the operating-system locale when supported; otherwise use English, while preserving an existing saved language.
- Test fixtures and examples must use only synthetic identities, usernames, emails, repository/project/team names, task/PR titles, and reserved domains such as `example`, `example.com`, or `example.invalid`; never copy real surnames, people, internal or public production domains, company names, project keys, repository names, team names, task names, PR titles, or credentials into code, tests, fixtures, docs, prompts, or sample configuration. Keep all sample credential values empty.
- Do not commit or push changes unless explicitly authorized.
- Every application PR must include release notes under `## Release notes` in the PR description. English notes are required; Russian notes may also be provided when applicable. Prefer Markdown between `<!-- release-notes:<lang> -->` and `<!-- /release-notes:<lang> -->` on their own lines. As a fallback, put a GitHub attachment link named `release-notes.<lang>.md` inside that language's block; links elsewhere in the PR are ignored. Use only nonempty Added/Changed/Fixed/Removed sections (translated for each language). Use `###` category headings in inline PR blocks and `##` in attached files; the workflow lifts inline headings for standalone release assets. Do not commit source notes to the repository. Inline text takes precedence over a link in the same block; the workflow publishes available notes as GitHub Release assets and uses English notes for the release description. Exclude changes that only affect development or mock modes from user-facing release notes. For PRs whose application changes only update libraries, use `### Changed` with `- Updated application libraries.` (Russian: `### Изменено` with `- Обновлены библиотеки приложения.`). Mention security fixes, bug fixes, or performance improvements only when verified. For other exceptional application PRs with no specific business/user-facing changes to report after excluding development/mock-only work, use the general English note `### Fixed` with `- Performance improvements and bug fixes.` The workflow currently allows a release to proceed when notes are missing, but that is a fallback and does not waive this requirement; add missing notes to the published release assets and description.

## Runtime and theme rules

- Do not launch the application just to inspect it or as a routine check. Launch it only when `computer_use` is required for a specific UI verification that cannot be covered by automated tests.
- Before launching, confirm that the required UI fields can actually be driven and verified with `computer_use`. If the app cannot be opened or the needed fields cannot be operated, do not launch it: use focused tests or the REST/backend path, or ask the user to perform the UI step.
- Do not leave a launched application running when no UI interaction and verification is planned.
- The application has exactly two selectable themes: white and dark. On startup, choose the initial theme from the operating system preference; after startup, the user may switch themes explicitly.


## Test scope for active development

- Keep automated tests deliberately minimal while the product is actively changing: tests are smoke checks, not exhaustive specification.
- For each changed critical flow, write at most one small positive-path test that proves the main behavior still works end to end.
- Do not add negative, edge-case, boundary, error-matrix, snapshot, or duplicate tests by default. Add them only when explicitly requested or when omitting them creates a material security, credential-leak, data-loss, or destructive-write risk.
- Prefer one representative test over testing every field, permutation, provider response, or UI state. Avoid tests that only duplicate TypeScript/Rust type checking or compile-time wiring.
- When behavior changes, update or delete obsolete tests instead of preserving compatibility with the old behavior. Keep test fixtures small and avoid broad mock graphs.
- Run the focused smoke test for the changed flow plus lint/build. Run the complete test suite only at a milestone, before release, or when explicitly requested.
- Before finishing, run `git diff --check`, inspect final diff/status, preserve unrelated dirty files, and never claim runtime behavior based only on compilation.


## shadcn/ui design system rules

- Menus attached to right-side controls align to the trigger's right edge (`align="end"`). Mark right-side Select containers/triggers with `data-menu-align="end"`; shared `SelectContent` carries this placement across its portal while explicit `align` takes precedence. Left-side selectors retain start alignment. Keep Radix viewport collision handling enabled.

- Select triggers default to the same 36 px / 13.5 px / 4 px vertical geometry as primary buttons. Select menus inherit their trigger's font size across the portal; compact triggers use 4 px vertical option padding. Compact card/subform field labels use 13 px text alongside their controls; preserve section headings and explicitly normal/page-size settings surfaces.

- Shared single-line text and numeric fields follow the selected button appearance. Filled without border and Minimal keep their borders transparent during hover, typing/focus, and validation; show primary-colored values for direct hover/focus and destructive-colored values for invalid input. Multiline text fields keep their normal text color on hover/focus and highlight their border instead, including in Minimal and Filled without border; preserve their inner padding. Warning/error feedback takes precedence. Keep label-hover isolation.

- Shared `Button` defaults (including main dialog confirmation/cancel actions) use 36 px height, 13.5 px text, and 4 px vertical padding; default icon actions are 36 px square. Minimal/Quiet changes appearance and horizontal alignment, not this default height. Preserve explicit smaller inline actions and the shared 32 px subform limits; use the large size only when intentionally required.

- Primary page filter/action rows use shared `PageToolbar` (also used by `PageHeader` actions): selects, combobox triggers, inputs, and text/icon actions are 36 px high with 13.5 px text; icon buttons are 36 px square. The same shared geometry applies to settings surfaces marked `data-action-size="page"` / `data-control-size="page"`, including General Settings. Do not repeat these sizes in feature components; keep compact subform controls at 32 px.

- Human-readable absolute dates use shared `formatDisplayDate` / `formatDisplayDateTime` from `@/lib/display-date`: `DD.MM.YYYY` in both languages, or `DD.MM` for compact chart axes where the year is redundant. Keep localized weekday/month names in calendar navigation and relative-time phrases. Do not change ISO command/storage timestamps, native date-input values, date keys, exports, or filename/log-date conventions solely to match display formatting.

- Explanatory `i` popovers use shared `InfoPopover` with localized `label` and `title`, its 12 px title/body typography, spacing, trigger, and anchored positioning. Feature content supplies only the explanation/examples; do not duplicate Popover/Info trigger markup or override the shared font size. Existing specialized metadata popovers must keep the same small typography when their distinct behavior requires custom markup.

- Minimal/Quiet text actions under card or subform headings have zero left padding so their leading content aligns with the heading/row above, including normal-size action surfaces. Shared compact action sizing must preserve this Minimal-specific alignment; do not apply it to Filled styles, sidebar navigation, toggle/picker controls, or main dialog footers.
- Minimal's left-aligned outer field values do not apply to editable search fields or inputs inside popover menus: preserve their 12 px inner padding on both sides (for example, Search sprints). Keep picker triggers under their labels left-aligned; distinguish them from the search input inside the opened picker.

- General Settings actions are primary controls even when placed in cards: use `data-action-size="page"` for shared 36 px button sizing and existing group gaps. Mark its larger language, appearance, and terminal picker surfaces with `data-control-size="page"`; compact retention fields retain subform sizing. Use `normal` only where the original geometry must remain independent of both shared scales.
- Small actions embedded beside labels keep their explicit small size with `data-action-size="inline"`; primary sizing must not enlarge them. Notifications test bells beside individual categories remain 24 px buttons with 14 px icons, including their pending/success icons.
- About actions and sidebar navigation use the same primary action geometry via `data-action-size="page"`, including 4 px vertical padding; keep navigation fill and selection behavior unchanged. Use `PageHeader spacing="grouped"` when a parent already provides the header/body gap so its standalone bottom margin does not double the spacing.
- Data integrations card headers are primary integration rows, not compact subforms. Preserve their 32 px action buttons and original icon sizes (Refresh 16 px, Edit/Delete 18 px) with `data-action-size="normal"` on the header.
- AI providers list-row actions retain 28 px buttons and 16 px icons; mark their action group with `data-action-size="normal"` so shared subform icon limits do not shrink them. Keep the compact AI providers section-header controls separate.
- Actions on object/result rows (teams, team members, PRs, Confluence search results, Daily participants/tasks, and similar rows with an identity, description, or status) retain their original icon sizes rather than the 14 px subform limit. Use `data-icon-size="normal"` when only icons need this exception, preserving compact button sizes and action gaps. Keep intentionally small badge actions at their explicitly defined size.
- Settings rows with a title and visible description use primary controls even inside nested sections. Use `data-control-size="page"` for shared 36 px field/picker geometry and `data-action-size="page"` for actions; reserve compact controls for compact rows and subform action groups. This includes General Settings language (UI and AI responses) and appearance rows.

- Groups of compact action buttons and fields in cards/subforms use the same shared 8 px horizontal gap, including provider/model pickers, numeric inputs with unit pickers, and a picker with its directly related action (such as AI provider group selection and Add). Shared CSS recognizes direct controls; mark wrapped fields with `data-slot="control-field"` and nested control groups with `data-slot="control-group"` instead of setting feature-local horizontal gaps. Keep these controls in their own flex group when a row also contains labels, values, or unrelated controls; do not shrink unrelated row spacing or the main dialog footer gaps.

- Hovering a field heading or associated label must not highlight or activate its control. Keep accessible label associations and normal click/keyboard focus behavior; use shared `Input`, `Textarea`, and picker primitives with `directPointerHover` for hover feedback instead of native control `:hover` (which can also match through a label). Composite editors must explicitly remove the inner control border and keep interaction feedback on their visible frame.
- Panel bodies containing nested panels use `p-4`: 16 px between their header/bottom boundary and the nested panels, with 16 px between peer panels. Keep compact text-only bodies separate from this rule; do not use their 12 px vertical padding around nested panels.

- Reserve the bottom-left dialog footer area for Close, Cancel, and equivalent actions that exit or abandon the form. Place all result-changing actions on the right, ordered from negative/destructive to neutral to affirmative, with the main positive action at the far right. Use shared red (`actionTone="delete"`) styling for dismissal/rejection and green (`actionTone="success"`) styling for affirmative decisions such as applying a reviewed revision; neutral alternatives keep `actionTone="neutral"`. Use `data-dialog-cancel` only on the single left-side button or its group, never on both the group and its children. Preserve this grouping when actions wrap.

- Match General Settings with a shared 16 px gap between peer panels or form blocks and between dialog headers, bodies, and footers. Use `DialogBody layout="sections"` for grouped dialog blocks; do not vary these gaps with the action-button style or add footer margins that duplicate the dialog gap. Keep compact spacing inside rows and between labels and their controls.
- Keep direct blocks in `DialogBody layout="sections"` from shrinking along the vertical flex axis. Long dialogs must scroll their body instead of collapsing or clipping cards and their content.
- Use shared compact sizing inside cards and subforms (`DialogBody` and custom containers marked `data-subform`): text actions, select/combobox triggers (including AI provider and model pickers), and single-line inputs are at most 32 px high with 13 px text, 14 px icons, 6 px icon/text gaps, and 10 px horizontal padding; icon actions are at most 32 px square. Preserve deliberately smaller controls and Quiet's left-aligned field values. Keep page-level controls and the main `DialogFooter` / `AlertDialogFooter` at their normal size. Scope custom subforms with `data-subform` instead of repeating feature-local size overrides; toggle, switch, checkbox, and multiline textarea controls keep their own geometry.
- Numeric fields must reserve enough content width for their visible digits in addition to both actual horizontal paddings and borders. Use `ManualNumberField`'s digit-based minimum width (and `minVisibleDigits` for compact counters); center numeric values so any spare width is balanced on both sides, while preserving Quiet's left alignment. Keep its padding budget synchronized with normal/compact control padding; never force a 24 px square or remove the minimum width while retaining normal field padding.
- Small inline counters such as Independent reviewers use `ManualNumberField size="compact"`: 24 px height and 6 px horizontal padding, with digit-based width that includes padding and borders. Do not reduce ordinary numeric settings fields with this variant.
- Keep action tooltips concise when the target is obvious from the button's row, card, or section: use shared localized action labels such as Edit, Delete, and Refresh instead of repeating the object type or name. Keep target-specific accessible names (`aria-label`) for repeated icon actions. Retain details in tooltips when needed to distinguish destinations, explain disabled states, or describe an otherwise ambiguous action.
- Use `CardHeader variant="section"` for section and settings-panel headings: full-width `bg-muted` fill, rounded top corners, and no bottom border or separator immediately below the header. Keep separators between body rows. Preserve compact header spacing where needed; ordinary object/result cards keep the default header. Add top spacing to the section body when its first row does not provide it.
- Direct children of a filled section header use only the panel's normal padding, with no additional left indentation. Add 16 px (`pl-4`) only for each deeper level of settings nested under another setting within the same panel (for example, Expand groups under Group by). A nested panel with its own filled header starts this rule anew for its direct children. Apply the inset once to the nested row or group, not separately to labels and controls. Align separators with their corresponding rows; omit a leading separator directly below the section header. Keep peer settings aligned and apply this rule to future changes without a separate spacing request.
- All Filled icon and text actions (including Save, Delete, Dismiss, rejection, creation, and affirmative actions), and picker controls keep their background fill unchanged on hover/focus across all surfaces; signal interaction through text/icon and border color rather than adding a third fill accent. Destructive actions use the shared destructive color for text/icon and border feedback, never a solid red background; this applies to `actionTone="delete"`, `actionTone="remove"`, and `variant="destructive"`, including confirmation dialogs. Muted section headers use the shared contrasting card fill. Preserve selected toggle states, keyboard focus rings, and the Quiet style.
- Filled text/icon actions outside sidebar navigation use a visible input-token border. Select triggers, outline combobox pickers, and numeric fields (`type="number"` or `inputMode="numeric"`/`"decimal"`, including ManualNumberField) use the shared `bg-control` surface with an input-token border: secondary on normal background/card surfaces, card inside muted section headers. Keep this surface-aware behavior shared rather than fixing individual controls; preserve pointer-hover and keyboard-focus feedback.
- Use a solid border and `px-4 py-3` (16 px horizontal, 12 px vertical) padding for empty states and standalone informational messages. Use `p-4` for compact settings subforms. Keep smaller spacing for embedded table/filter rows; do not copy indentation or leading separators from nested settings rows into peer fields.
- Alternate panel fill at every nesting level based on the actual parent surface: `bg-background` → `bg-card` → `bg-background`, repeating for deeper panels. Reserve muted fills for special elements such as table headers and status indicators, not generic nesting levels. Labels above controls have a shared minimal 4 px left inset through `Label`/`FieldLabel`; do not repeat that inset in feature components. Labels beside controls use `alignment="inline"` with no field-heading padding; horizontal `Field` labels also have no inset. Section headings do not receive this field-label inset.
- Before implementing any UI or styling change, load and follow your agent's shadcn/ui skill if available; otherwise consult the official shadcn/ui documentation. In both cases, apply the project-specific constraints below where they are more specific.
- `components.json` is the source of truth for shadcn/ui CLI configuration. Keep `style: "default"`, CSS variables enabled, the Lucide icon library, and the configured `@/*` aliases in sync with the repository.
- Components are source-owned under `frontend/components/ui`. Add or refresh them with `npx shadcn@latest add <component>` only after checking the current official component documentation, then review the generated diff before keeping it.
- Use Tailwind CSS v4's CSS-first setup (`@import "tailwindcss"` and `@tailwindcss/vite`); do not add a legacy `tailwind.config.*` solely for shadcn/ui.
- Use semantic CSS-variable tokens (`background`, `foreground`, `primary`, `muted`, `accent`, `destructive`, `border`, `input`, `ring`, and their foreground pairs) through `@theme inline`. Do not hard-code theme colors in migrated UI components.
- The application has only White/light and Dark themes. Preserve the existing `data-theme` selector contract; do not add a competing theme provider, `.dark` state store, or third selectable theme.
- Import shared utilities through `@/lib/utils` and compose classes with `cn`. Keep `@/*` imports resolvable in both TypeScript and Vite.
- Add only dependencies required by the selected shadcn/ui registry entry. Do not replace source-owned primitives with a hosted component runtime.
- Every new primitive or customization needs focused tests where behavior is meaningful, followed by `npm test -- --run`, `npm run lint`, and `npm run build`.
